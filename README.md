# Lockout Lab
### 로그인 차단 정책의 효과와 정상 사용자 영향을 함께 비교하는 웹앱

**같은 로그인 요청에 차단 정책을 적용하면 공격 검사는 얼마나 줄고, 정상 사용자는 얼마나 막힐까요?**

Lockout Lab은 이 질문을 직접 확인하는 논문 기반 보안 학습 도구입니다. 공격 간격과 차단 규칙을 선택하면 동일한 합성 요청에 **차단 없음**과 **선택한 차단 정책**을 적용하고, 두 정책의 결과와 요청별 처리 기록을 보여줍니다.

[**앱 바로 사용하기**](https://song-youngchan-career.ksyji123.chatgpt.site/lockout-lab/) · [포트폴리오](https://song-youngchan-career.ksyji123.chatgpt.site/#works) · [논문 원문](research/paper.md) · [확장 계획서](plan.md)

## 1. 만든 이유

보안 솔루션 엔지니어를 준비하면서, 차단 규칙의 효과를 숫자로 설명하고 정상 사용자에게 미치는 영향까지 확인하는 작업을 해 보고 싶었습니다.

기반 연구인 **「로그인 실패 후 일시 차단 정책의 효과와 정상 사용자 차단」**에서는 같은 요청 자료를 두 정책에 적용했습니다. 5회 연속 실패 후 30초 동안 계정을 잠그면 공격 요청을 실제로 검사하는 횟수는 줄었지만, 정상 요청도 함께 차단됐습니다.

논문의 결과를 읽는 데서 끝내지 않고 다음을 직접 확인할 수 있도록 앱으로 옮겼습니다.

- 공격 간격에 따라 차단 정책의 결과가 어떻게 달라지는지
- 실패 횟수와 차단 시간을 바꾸면 정상 접근에 어떤 영향이 생기는지
- 올바른 비밀번호를 입력한 정상 요청도 계정 잠금 때문에 거절될 수 있는지

보안 정책을 배우는 취업 준비생과 차단 정책의 효과·부작용을 설명하려는 초급 담당자를 대상으로 합니다.

## 2. 현재 구현한 기능

| 기능 | 사용자가 할 수 있는 일 |
| --- | --- |
| 공격 조건 선택 | 평균 공격 간격을 빠름 0.5초·중간 2초·느림 10초로 변경 |
| 차단 규칙 조절 | 연속 실패 임계값과 차단 시간을 입력하고 다시 계산 |
| 두 정책 비교 | 차단 없음과 현재 규칙의 공격 검사 횟수·정상 로그인 성공 건수 비교 |
| 정상 영향 확인 | 정상 요청 차단율과 정답 정상 요청의 차단 건수 확인 |
| 요청 기록 조회 | 반복 번호 1~30을 선택하고 정상 요청·차단된 정상 요청·모든 요청으로 필터링 |
| 결과 내보내기 | 적용한 조건, 집계 결과, 해석 한계가 담긴 JSON 저장 |

## 4. 1분 사용 방법

1. **공격 평균 간격을 선택합니다.** 처음에는 빠름 조건과 논문 기준 5회·30초 결과가 표시됩니다.
2. **차단 규칙을 바꾸고 ‘이 규칙으로 비교’를 누릅니다.** 공격 검사 감소율과 정상 요청 차단율을 함께 확인합니다.
3. **아래 표에서 ‘차단된 정상 요청’을 선택합니다.** 정답 입력 여부, 차단 없는 결과, 현재 규칙의 결과와 해제 시각을 비교합니다. 필요한 결과는 JSON으로 저장합니다.

공격 간격을 바꾸면 즉시 재계산됩니다. 실패 횟수·차단 시간을 수정한 뒤에는 비교 버튼을 눌러야 결과가 갱신됩니다.

## 5. 논문 결과를 앱에 반영한 방법

### 데이터

과제10 원본 `data/requests.csv`의 합성 요청 **48,533건**을 `data.js`로 변환했습니다. 각 요청은 가상 시각, 정상 요청 여부, 입력 정답 여부로 구성됩니다. 브라우저에서 사용할 수 있도록 표현을 바꾸었으며 원본의 요청 순서를 유지했습니다.

| 실험 조건 | 내용 |
| --- | --- |
| 비교 단위 | 같은 요청 묶음에 두 정책을 각각 적용 |
| 계정 범위 | 공격과 정상 요청이 잠금 상태를 공유하는 단일 계정 |
| 시간 | 반복당 600초 미만의 가상 시간 |
| 공격 간격 | 평균 0.5초·2초·10초, 각 간격에 0.8~1.2배 변동 |
| 반복 수 | 조건별 30쌍, 전체 90쌍·180회 정책 평가 |
| 정상 요청 | 반복당 20건, 생성 시 오입력 확률 10% |
| 공격 요청 | 모두 오답으로 설정 |
| 기준 정책 | 5회 연속 실패 후 30초 차단 |

세 공격 조건은 같은 정상 요청 자료를 사용합니다. 조건별 정상 요청 600건을 서로 다른 실제 사용자 600명의 관측으로 해석하지 않습니다.

### 상태 처리 규칙

논문의 Python 모형을 `engine.js`로 옮겼습니다.

1. 임계값에 도달한 실패 요청까지는 검사하고, 그 시각부터 차단을 시작합니다.
2. 차단 중 요청은 비밀번호 검사를 건너뛰며 차단 시간을 연장하지 않습니다.
3. 해제 시각과 정확히 같은 시각의 요청은 검사합니다.
4. 정상 로그인 성공 시 또는 차단 만료 후 첫 요청에서 실패 횟수를 0으로 초기화합니다.
5. 정상 요청의 오입력도 실패 횟수에 포함합니다.

기본값 **5회·30초**에서는 **‘논문 재현’**, 다른 설정에서는 **‘추가 탐색’**으로 표시합니다. 추가 탐색은 원본 요청에 새 규칙을 적용한 계산이며, 논문에서 해당 설정을 검증했다는 뜻은 아닙니다.

## 6. 재현되는 결과와 읽는 방법

5회·30초 설정에서 다음 결과가 재현됩니다.

| 공격 평균 간격 | 공격 검사 건수: 차단 없음 → 차단 적용¹ | 공격 검사 감소율² | 정상 요청 차단율³ |
| --- | ---: | ---: | ---: |
| 빠름 · 0.5초 | 1,199.07 → 98.17 | 91.81% | 92.17% |
| 중간 · 2초 | 299.27 → 85.87 | 71.30% | 73.83% |
| 느림 · 10초 | 59.43 → 47.60 | 19.90% | 27.00% |

1. 공격 검사 건수는 반복당 평균입니다.
2. 공격 검사 감소율은 각 반복에서 `(차단 없는 검사 건수 − 차단 적용 검사 건수) / 차단 없는 검사 건수 × 100`을 구한 뒤 30회의 산술평균을 냅니다.
3. 정상 요청 차단율은 `차단된 정상 요청 / 제출된 정상 요청 × 100`입니다.

예를 들어 빠름 조건에서는 정상 요청 600건 중 553건이 차단됩니다. 정답 정상 요청 542건 가운데서도 497건이 차단되고, 정상 로그인 성공 건수는 542건에서 45건으로 줄어듭니다.

이 결과가 보여주는 것은 **공격 검사 기회를 제한하는 효과와 정상 접근 손실이 함께 발생한다는 점**입니다. 공격 검사 감소율 하나만 보고 서비스에 적합한 정책이라고 판단할 수는 없습니다.

## 7. 입력 오류와 결과 저장

### 허용하는 값

| 입력 | 허용 범위 |
| --- | --- |
| 연속 실패 횟수 | 1~20의 정수 |
| 차단 시간 | 1~300초의 정수 |

빈칸, 음수, 0, 소수 또는 범위 밖 값을 넣으면 오류 안내를 표시합니다. 마지막으로 성공한 비교 결과는 유지하며, 정상값을 입력하거나 **‘논문 기준 5회·30초로 복원’**을 누르면 다시 계산할 수 있습니다.

선택한 반복에 차단된 정상 요청이 없으면 빈 결과 안내를 표시하고 다른 반복이나 필터를 선택할 수 있습니다.

### 내보내는 JSON

파일명은 `lockout-lab-{공격조건}-{실패횟수}-{차단시간}.json` 형식입니다.

- 기반 논문 제목과 합성 자료의 조건
- 논문 재현 또는 추가 탐색 구분
- 선택한 공격 간격·실패 임계값·차단 시간
- 공격 검사 감소율과 정책별 평균 검사 건수
- 정상 요청·차단·정상 로그인 성공 건수
- 결과를 해석할 때의 한계

입력만 수정하고 비교를 실행하지 않았다면 **현재 화면에 표시된 마지막 계산 결과**를 저장합니다.

## 9. 검증 방법

### 자동 검증

Node.js 18 이상이 있다면 저장소 폴더에서 실행합니다. 추가 패키지는 필요하지 않습니다.

```bash
node verify.cjs
```

성공하면 JSON에 `"status": "PASS"`가 출력됩니다.

| 검증 항목 | 확인 내용 |
| --- | --- |
| 논문 결과 재현 | 세 조건의 감소율, 평균 검사 건수, 정상 차단·성공 건수와 원본 집계 대조 |
| 요청 건수 보존 | 각 정책에서 제출 건수 = 검사 건수 + 차단 건수 |
| 차단 시작 경계 | 임계값에 도달한 요청은 검사한 뒤 차단 시작 |
| 차단 종료 경계 | 해제 시각과 같은 시각의 요청 검사 |
| 차단 유지 규칙 | 차단 중 요청이 해제 시각을 연장하지 않음 |
| 성공 후 초기화 | 정상 로그인 성공 후 실패 누적 초기화 |
| 잘못된 값 | 범위 밖 값·소수·NaN·무한대 거부 |
| 자료 건수 | 원본 합성 요청 합계 48,533건 |

제작 시 기본 앱과 새 폴더에 압축 해제한 실행 묶음에서 위 검증을 통과했습니다.

### 브라우저 확인

제작 과정에서 Chrome으로 공격 조건 전환, 규칙 변경, 빈칸·소수 입력 처리, 복원, 정상 차단 기록 필터와 JSON 다운로드를 확인했습니다.

직접 확인할 때는 다음 순서로 진행할 수 있습니다.

1. 5회·30초의 세 공격 조건이 위 결과 표와 일치하는지 확인합니다.
2. 규칙을 변경해 추가 탐색 결과를 확인하고, 잘못된 입력 후 복원합니다.
3. 차단된 정상 요청을 조회하고 저장한 JSON의 수치가 화면과 같은지 확인합니다.

자동 검증은 계산 모형을 검사합니다. 화면 배치나 다운로드 동작은 브라우저에서 별도로 확인해야 합니다.

## 10. 적용 범위와 한계

이 프로젝트는 **합성 자료를 이용한 사건 기반 모의실험**입니다.

- 실제 인증 서버, 비밀번호 해시 연산, CPU 사용량, 지연 또는 네트워크 성능을 측정하지 않았습니다.
- 공격은 모두 실패하도록 생성했으므로 계정 탈취 확률이나 공격 성공률을 계산할 수 없습니다.
- 요청 생성 자체는 계속되므로 검사 감소를 네트워크 트래픽 감소로 해석하지 않습니다.
- 공격과 정상 요청이 단일 계정을 공유하는 가정입니다. 다중 계정, 분산 공격, IP별 제한과 사용자 복구 행동을 대표하지 않습니다.
- **5회·30초는 실험 조건이며 실제 서비스의 권장 설정이 아닙니다.**
- 방화벽 연동, 실시간 이상 탐지와 사전·사후 결합 방어는 현재 구현하거나 효과를 검증한 기능이 아닙니다.

앱 데이터에는 실제 이용자의 실명·연락처·계정 비밀번호가 없습니다. API 키와 환경 변수도 사용하지 않습니다. 계산과 결과 생성은 브라우저 안에서 수행하며, 사용자가 외부 링크를 누르는 경우에는 해당 사이트로 이동합니다.

## 11. 후속 확장 계획

BR-B에서 만든 기본 앱을 출발점으로 다음 기능을 계획했습니다. **아래 항목은 아직 구현 전입니다.**

| 순서 | 추가할 기능 | 완료 시 확인할 내용 |
| --- | --- | --- |
| 1 | 정책 A/B 동시 비교 | 같은 요청에 두 사용자 지정 정책을 적용하고, 같은 설정이면 같은 결과가 나옴 |
| 2 | 정책 저장·불러오기·삭제 | 새로고침 후 복구, 개별 삭제, 저장 오류가 발생해도 앱 사용 가능 |
| 3 | 비교 보고서 확장 | 두 정책의 조건·결과·한계를 JSON·CSV로 내보내고 화면과 대조 |

계획과 점검 기준은 [plan.md](plan.md)에 정리했습니다. 현재 제공되는 단일 규칙 비교와 JSON 저장 기능을 확장 기능 완료로 표시하지 않습니다.

## 12. 제작 과정과 역할

**작성자: 송영찬**

기반 연구에서는 가상머신 없이 실행 가능한 로그인 차단 모의실험을 주제로 선택했고, 정상 사용자 차단 문제와 사전 접근 규칙·사후 이상 탐지의 연계를 후속 검토 방향으로 제안했습니다.

AI는 원본 자료 변환, JavaScript 계산 모형, 화면, 검증 코드와 문서 초안 작성을 도왔습니다. 이번 앱은 논문에서 실제로 계산한 결과를 직접 조작하고 확인할 수 있도록 구성했습니다. 후속 결합 방어 제안은 검증된 결과와 구분했습니다.

이 저장소에서 확인할 수 있는 작업은 **연구 결과의 앱 적용, 상태 처리 규칙 구현, 정상 접근 영향의 시각화, 원본 결과 대조 검증**입니다.
